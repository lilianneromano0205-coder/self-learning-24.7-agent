# PART I — SECURITY AND PLATFORM HARDENING
## P0 — Investigate and eliminate detached-child escape from host execution
Current concern:
The default configuration uses:
`sandbox = "host"`
The host backend is not filesystem/process isolation. `controlplane.py` seals control files before a model-authored process and compares/reverts them afterward.
This may leave a TOCTOU hole:
* model-authored parent process launches a detached child;
* parent exits;
* control-plane comparison runs before the delayed child writes;
* control plane reports CLEAN;
* detached child later mutates protected state.
### Required work
Build a safe local regression fixture that attempts:
1. spawn delayed/detached child;
2. parent process exits;
3. child waits;
4. child attempts to alter `settings.toml` or another CONTROL file;
5. test verifies the mutation cannot survive or cannot happen.
Test multiple process-detachment mechanisms relevant to supported operating systems without creating general-purpose persistence tooling.
If the current host backend cannot guarantee the invariant, do not patch it with command-string regexes.
Preferred architectural solutions:
* make Docker or an equivalent isolated backend mandatory for shell-capable autonomous work;
* or introduce process-tree containment and filesystem restrictions that actually hold after the parent exits;
* clearly classify `host` as unsafe/developer-only if it cannot provide the same security guarantee.
The final invariant should be:
> A model-authored process and every descendant process lose the ability to mutate protected authority state after the execution authority declares the operation finished.

## P0/P1 — Protect authority/seal state outside the expert root
Goal contracts and some other authority records are deliberately sealed outside the expert working root.
That architecture is strong under actual containment but potentially weak under unrestricted host execution because a process may be able to access both:
* the in-expert contract;
* the fleet-home seal ledger.
Audit all files outside the expert root that affect:
* verification;
* ownership;
* promotion;
* capabilities;
* contracts;
* federation trust;
* grants;
* training promotion;
* variant promotion;
* proof status.
### Specific contract issue
Inspect `contract._sealed_hash()`.
The contract system appears to use the last matching seal row as authoritative, while newer frontier code deliberately uses first-seal-wins plus conflict detection.
Evaluate whether an attacker able to append a new matching seal could make a modified contract appear legitimate.
### Required outcome
Protected authority state must remain independent of a model-authored process even when that process attempts to modify both the working copy and the authority reference.
Prefer:
* kernel/container isolation;
* immutable/owner-only authority storage;
* first-seal-wins or explicit generation/version semantics where appropriate;
* conflict -> TAMPER;
* append-only ledgers that cannot make a later untrusted append authoritative.
Add regression tests.

## P1 — Build an isolated acquisition arena
Current acquisition staging improved by moving installation into temporary staging rather than directly into `capabilities/`.
However, inspect whether the network-enabled package installer still receives the entire expert workspace through `/work`.
If so, a malicious package/build backend may be able to read:
* courses;
* research;
* memory;
* artifacts;
* task outputs;
* customer/workspace data;
and send those contents through network egress.
Environment-secret scrubbing does not solve filesystem disclosure.
### Required architecture
Create a dedicated acquisition sandbox/arena such as:
`tmp/acquire-arena-*/input`
`tmp/acquire-arena-*/output`
Only explicitly required package input should enter the network-enabled environment.
The installer must not see the complete expert root.
After installation:
1. trusted host validates output;
2. verify no forbidden symlinks/special files/path escapes;
3. calculate hashes;
4. run the sealed capability probe;
5. atomically promote to `capabilities/<name>`;
6. preserve provenance/version data.
### Regression
Plant a sentinel outside the acquisition arena and verify a package-build test fixture cannot read it.

## P1 — Fix hosted sandbox filesystem semantics
Audit Docker, E2B, Daytona, Cloudflare, and any other execution backends.
Docker has bind-mounted filesystem semantics.
Hosted backends appear to execute remotely using a remote working directory but may not upload the local expert workspace or download generated files afterward.
That means the common `sandbox.run()` interface may currently promise semantics that different backends do not actually share.
### Required design
Define the execution contract explicitly.
For backends that support workspace-mutating workloads:
1. create session;
2. upload only authorized workspace subset;
3. execute;
4. collect declared artifacts;
5. validate artifact paths/content;
6. download;
7. atomically apply to local workspace;
8. destroy remote environment.
Until implemented, fail closed for operations that require filesystem round-tripping.
Do not report a remote operation as having modified the local expert when no artifact transfer occurred.

## P2 — Make effect semantics precise
The effects ledger has a good write-ahead design.
However, without transactional support from an external service, strict exactly-once delivery is impossible across:

# PART VIII — VERIFICATION HIERARCHY
Preserve the core invariant:
> Mechanical/frozen graders remain supreme wherever they can decide the task.
Add optional verification layers for open-ended tasks.
Recommended hierarchy:
### L0 — Mechanical/formal
Tests, compiler, schema, deterministic checks, frozen acceptance.
### L1 — Cheap specialist verifier
Task-specific classifier/checker/PRM.
### L2 — Adversarial verifier
Search for counterexamples, missing requirements, contradictions, unsafe behavior.
### L3 — Rubric/evidence verifier
Generative verifier using explicit rubric and evidence.
### L4 — Frontier verifier
For high-value irreducibly subjective cases.
Rules:
* higher probabilistic/verbal layers never override a failing L0 mechanical test;
* verifier outputs are logged separately from worker outputs;
* verifier family should differ from actor family for high-value work when feasible;
* measure verifier false-positive/false-negative rates.
